== Getting started with secure development

This project guides you through the Secure Development Lifecycle using the Cyberismo tool. It is structured into phases and adoption steps that align with your product's journey from initial planning to production operations.

=== How this project is organized

Each phase contains security controls and tasks relevant to that stage:

* *{{#report}}"name": "xref", "identifier": "secdeva_phase_foundation"{{/report}}* — Establish security governance, training, and tooling before development begins.
* *{{#report}}"name": "xref", "identifier": "secdeva_phase_design"{{/report}}* — Define security requirements, perform threat modeling, and create specifications.
* *{{#report}}"name": "xref", "identifier": "secdeva_phase_implementation"{{/report}}* — Apply secure coding practices and manage third-party dependencies.
* *{{#report}}"name": "xref", "identifier": "secdeva_phase_verification"{{/report}}* — Conduct security testing and validate that requirements are met.
* *{{#report}}"name": "xref", "identifier": "secdeva_phase_releases"{{/report}}* — Prepare secure release artifacts and documentation.
* *{{#report}}"name": "xref", "identifier": "secdeva_phase_operations"{{/report}}* — Handle vulnerability disclosures, patches, and end-of-life planning.

=== Adoption steps

Controls and tasks are assigned an adoption step (1–3) so you can roll out secure development incrementally:

* *Step 1* — Essential practices. Start here to establish baseline security across all phases.
* *Step 2* — Strengthened practices. Expand coverage once Step 1 is in place.
* *Step 3* — Advanced practices. Achieve standards compliance.

Focus on completing all Step 1 items before moving to Step 2. This ensures the most critical security practices are in place first.

=== Where to start

[mermaid]
----
flowchart LR
    subgraph F[Foundation]
      direction TB
      R[Assign people to security-related project roles] --> C[Ensure competence]
    end
    subgraph D[Design]
      direction TB
      SC[Document product security context] --> TM[Manage threat models]
      TM --> RI[Identify risks]
      RI --> SR[Derive security requirements]
    end
    F --> D
    D --> Next[Perform security controls scoping]
----

. Fill in the project scope and objectives on the parent card *{{#report}}"name": "xref", "identifier": "secdeva_project"{{/report}}*.
. *Assign people to security-related project roles* — Define who is responsible for security in the project. Without clear ownership, tasks will not get done.
. *Ensure competence* — Verify that assigned people have adequate cybersecurity knowledge, and arrange training where needed.
. *Document product security context* — Describe the product's operating environment, trust boundaries, and key security assumptions. This context guides threat modeling and requirements work.
. *Manage threat models* — Model your system's architecture and identify how it could be attacked. This reveals the risks that matter most.
.. You are able to indentify and document risks for the entire product or for a specific asset
. *Derive security requirements* — Turn identified risks into concrete security requirements that guide implementation and testing.
.. You are able to write security requirements for the product or for a specific asset
. *Preform security controls scoping* — Go through security controls to perform risk based security controls scoping
. As development progresses, address controls in each subsequent phase.
. Use *Status & next steps* to track overall progress and identify gaps.

TIP: You do not need to complete all phases at once. Start with Foundation and Design, then expand as your product matures.
